系统架构概览

报文/消息类型 Lane 0 控制字符 O-code值（位34:37） PCS块类型 用途

关键区分点：MII接口上通过Lane 0的不同控制字符（0x9C vs 0x5C）进行初级识别，PCS编码后的O-code值（0x0 vs 0x6）进行最终验证。CtlOS必须满足D4[3:0] = 0x6的强制要求。
PCS层必需改进（64B/66B编码）
编码侧修改（Table 6-4）
MII Lane 0控制字符 0x5C 映射为：
  • 块同步头：'10'（2比特）
  • 块类型：0x4B（8比特）
  • O-code：0x6（4比特）
  • 数据有效载荷：D1-D7（56比特）
解码侧修改（Table 6-5）
使用无状态解码规则：
  • O-code[34:37] = 0x0 → MII_D0=0x9C
  • O-code[34:37] = 0x6 → MII_D0=0x5C
  • 支持包抢占（Preemption）
  • CtlOS可在数据包中间插入
状态机改进（Table 6-6）
从状态机改为无状态规则：
  • Reset=1：输出LBLOCK_T
  • Reset=0：直接ENCODE(tx_raw)
  • 无需跟踪历史块状态
  • 降低延迟和复杂度

RS层必需改进
发送端（TX RS）
功能：将MAC请求转换为MII信号
  • MAC发送CtlOS请求
  • RS输出MII信号：
  • TXD[7:0]=0x5C（Lane 0）
  • TXD[63:8]=D1:D7数据
  • 必须8字节对齐到Lane 0
接收端（RX RS）
功能：识别并转发CtlOS消息
  • 检测RXC[0]=control且RXD[7:0]=0x5C
  • 验证有效CtlOS
  • 向MAC层发送指示
  • 不影响DATA_VALID_STATUS
  • 跳过CtlOS用于Start字符判断
CtlOS插入规则
约束条件：
  • 不能在包前256字节内
  • 最小间距：≥400字节
  • 推荐间距：~1600字节
  • ≤2%链路带宽占用
  • 不破坏802.3包完整性
RS DATA_VALID_STATUS处理：单个有效CtlOS不导致DATA_VALID_STATUS=DATA_NOT_VALID。在2048比特窗口内多个CtlOS才被视为错误。CtlOS前的数据用于确定后续Start字符的DATA_VALID状态。
MAC层集成要求
发送端（TX MAC）
  • 支持CtlOS消息请求接口
  • 通过MA_DATA.request传递
  • 允许CtlOS抢占数据包
  • 维持相对顺序关系
  • 确保包完整性和连续性
接收端（RX MAC）
  • 识别和分类CtlOS消息
  • CF_Update：直接转发到CBFC层
  • CC_Update：转发到MAC客户端
  • 保持数据包接收顺序
  • 通过MA_CONTROL.indication指示
CtlOS消息类型（Table 5-29）
  • LLR ACK：0x01
  • LLR NACK：0x02
  • LLR INIT：0x03
  • LLR INIT_ECHO：0x04
  • CBFC CF_Update：0x10

① MAC层：生成CtlOS消息请求
↓
② MAC检查先决条件：
  • 距上一个包 ≥256字节
  • 距上一个CtlOS ≥400字节
  • 选择CtlOS类型（ACK/NACK/CF_Update）
↓

  • 接收MA_DATA.request
  • 在MII输出CtlOS：
  • TXD[7:0] = 0x5C
  • TXC[0] = control
  • TXD[63:8] = D1:D7
↓
④ PCS编码器（修改版）：
  • 检测MII_D0 = 0x5C
  • 应用Table 6-4映射规则
  • 使用无状态编码规则
  • 生成64B/66B块
↓
⑤ 64B/66B块格式输出：
  • Sync = '10'
  • Block Type = 0x4B
  • O-code = 0x6 ✓ 关键
  • 数据有效载荷 D1:D7
↓
⑥ 发送至物理介质
CtlOS完整处理流程（接收端）
① 接收64B/66B块
↓
② PCS解码器检查：
  • 验证Sync = '10'
  • 验证Block Type = 0x4B
  • 检查O-code[34:37]
↓
③ PCS判决分支：
  • IF O-code = 0x0 → IDLE (0x9C)
  • IF O-code = 0x6 → CtlOS (0x5C)
  • 应用Table 6-5解码规则
↓
④ RS层（接收端）：
  • 从MII读取RXD/RXC
  • IF RXC[0]=1 AND RXD[7:0]=0x5C
  • 有效CtlOS检测到
  • 不影响DATA_VALID_STATUS
↓

  • 发送MA_CONTROL.indication
  • 附带CtlOS数据
  • 维持包接收顺序
↓
⑥ MAC分类处理：
  • CF_Update → CBFC层
  • LLR_ACK/NACK → LLR层
  • 其他 → 相应处理模块
↓
⑦ 消息处理完成
不支持LLR的芯片兼容性分析
✓ 情况1：完全兼容
条件：芯片虽然不支持LLR协议栈，但在物理层实现了PCS改进（第6.2.3节规范）。

能力：
  • ✓ 能够编码CtlOS消息（O-code=0x6）
  • ✓ 能够解码CtlOS消息
  • ✓ 正确识别0x5C控制字符
  • ✓ 支持无状态64B/66B处理
应用场景：作为网络中继或交换设备，可以透传CtlOS消息而无需理解其内容。
⚠ 情况2：部分兼容
条件：芯片在某个方向（TX或RX）支持CtlOS，但另一方向不完全支持。

能力：
  • ~ 可能只支持编码（TX方向）
  • ~ 可能只支持解码（RX方向）
  • ~ O-code识别不完整
  • ~ 对抢占支持有限
后果：单向数据流可能正常，但双向通信会出现问题。
✗ 情况3：不兼容
条件：芯片完全按照标准IEEE 802.3规范实现，没有PCS改进。

问题：
  • ✗ PCS编码器不支持O-code=0x6生成
  • ✗ PCS解码器不识别O-code=0x6
  • ✗ 0x5C控制字符被视为错误
  • ✗ 可能导致链路错误或中断
解决方案：通过LLDP协商禁用LLR和CBFC功能，回退到标准IEEE 802.3模式。
协商机制（第5.3节）：两台设备在链路建立时通过LLDP交换UE Link Negotiation TLVs。如果远端不支持LLR（llr_remote_capability=0），本地设备应禁用LLR功能（llr_mode_local=OFF）。这确保了与标准IEEE 802.3设备的互操作性。

常见故障排查指南
问题：无法识别CtlOS
可能原因：
  • PCS解码器未检查O-code=0x6
  • 使用了旧的IEEE解码规则
  • 0x5C控制字符被错误处理
排查步骤：
  • 验证O-code[34:37]的值
  • 检查解码器状态机
  • 确认无状态规则实现
问题：CtlOS导致链路错误
可能原因：
  • 对齐问题：未8字节对齐
  • 间距违规：两个CtlOS间距＜400字节
  • RS层处理错误
排查步骤：
  • 检查MII时序和对齐
  • 验证CtlOS间距计算
  • 使用逻辑分析仪采样
问题：数据对齐错误
可能原因：
  • CtlOS未8字节对齐到Lane 0
  • MII接口时序问题
  • RS层对齐检查缺失
排查步骤：
  • 检查CtlOS的Lane 0位置
  • 验证8字节边界对齐
  • 确认RS对齐约束
问题：数据丢失或不完整
可能原因：
  • PCS编码错误
  • RS层丢弃了CtlOS
  • MAC层未正确识别
排查步骤：
  • 检查O-code编码
  • 验证Block Type 0x4B
  • 使用示波器采样MII信号

🎯 IDLE vs CtlOS

IDLE（0x9C）：
• IEEE标准序列有序集
• Lane 0 = 0x9C
• O-code = 0x0
• 仅包间可用

CtlOS（0x5C）：
• UE链路层消息
• Lane 0 = 0x5C
• O-code = 0x6 ⭐
• 包内任意可用

⚙️ PCS层关键改动

编码器（Table 6-4）：
MII 0x5C → O-code=0x6

解码器（Table 6-5）：
O-code[34:37]判决

状态机（Table 6-6）：
无状态规则

关键字段：
• Block Type: 0x4B
• D4[3:0]: 0x6

📋 RS层关键改动

发送端：
• MA_DATA.request → TXD[7:0]=0x5C
